# 私人资源编辑与删除设计

- 日期：2026-09-07
- 状态：已确认
- 范围：个人 Space 中私人资源的编辑与删除

## 1. 目标与非目标

登录用户可以在自己的 Space 中编辑或删除本人添加的私人资源。公共资源继续只提供 Mark，不显示编辑或删除入口。

本阶段不加入资源公开、管理员审核、批量删除、回收站和版本历史。这些能力没有当前需求，提前实现会增加权限与恢复逻辑。

## 2. 交互设计

私人资源卡片右上角显示 `⋯` 操作菜单，展开后提供“编辑”和“删除”。选择该方案是因为它能保持卡片简洁，并与公共资源右上角的 Mark 星标形成清晰区别。

编辑复用私人资源表单组件：

- 新增模式使用空表单，提交到 `createResource`。
- 编辑模式使用当前资源预填表单，提交到 `updateResource(resourceId, input, reviewed)`。
- 编辑首次提交使用 `reviewed=false`。只有 RPC 返回 `similar_review_required` 时，用户才可以明确确认并以 `reviewed=true` 再次提交。
- 编辑成功后关闭弹窗；校验、重复、上限或网络失败时保留用户输入。

删除使用独立确认弹窗，显示资源名称，避免误删。只有用户再次点击“确认删除”才调用删除回调。删除成功后关闭弹窗；删除失败时弹窗保持打开并显示可重试提示。

## 3. 组件与责任边界

| 单元 | 负责 | 不负责 |
|---|---|---|
| `ResourceCard` | 根据资源类型展示公共 Mark 或私人 `⋯` 菜单；发出编辑、删除意图 | 调用 API、保存弹窗状态 |
| `PrivateResourceDialog` | 新增/编辑表单状态、前端字段校验、相似推荐确认和安全错误提示 | 判断数据库权限与最终写入资格 |
| `DeleteResourceDialog` | 二次确认、等待状态、失败后重试 | 直接导入 Supabase/API |
| `SpacePage` | 保存当前编辑/删除目标，组合弹窗与回调 | 拼接数据库查询 |
| `App` | 将 Hook 提供的 `updateResource`、`deleteResource` 注入 Space | 实现编辑或删除业务规则 |
| `useResourceActions` | 调用 API、成功后刷新 Space、记录结构化错误日志 | 渲染 UI |
| Postgres RPC/RLS | 验证资源属于当前用户，原子执行更新或删除 | 控制弹窗交互 |

页面与组件不得直接导入 Supabase client 或 `resourceApi`。

## 4. 数据流

### 编辑

```text
私人资源菜单 → 编辑 → 预填表单
→ 本地字段校验
→ updateResource(resourceId, input, false)
→ saved：刷新 Space 并关闭
→ similar_review_required：展示推荐
→ 用户确认 → updateResource(resourceId, input, true)
→ 其他业务状态：阻止保存并保留表单
```

更新 RPC 检查重复资源时排除当前资源 ID，避免把资源自身误判为重复。权限由 `auth.uid()` 与数据库所有者校验决定，前端传入的资源 ID 不能代表权限。

### 删除

```text
私人资源菜单 → 删除 → 二次确认
→ deleteResource(resourceId)
→ 数据库验证所有权并删除
→ 成功：刷新 Space 并关闭
→ 失败：保留确认弹窗并显示重试提示
```

数据库外键的 `ON DELETE CASCADE` 负责删除该资源对应的主题关系与浏览历史。删除不可恢复，因此必须二次确认；本阶段不实现软删除。

## 5. 错误与日志

- 表单字段错误显示在对应字段旁，不写错误日志。
- RPC 返回的预期业务状态使用稳定状态码渲染，不作为异常日志。
- 网络错误、未知 API 错误和越权错误由 `useResourceActions` 记录现有结构化事件：`private_resource_update_failed` 或 `private_resource_delete_failed`。
- 日志包含 `resourceId`；编辑日志额外包含 `category`。不记录 URL、描述和标签，避免把用户私人内容写入日志。
- UI 只显示安全、可操作的翻译文案，不显示数据库原始错误文本。

## 6. 测试与验收

组件测试覆盖：

1. 公共资源只显示 Mark，不显示私人资源菜单。
2. 私人资源显示菜单，不显示 Mark；编辑和删除分别发出正确资源。
3. 编辑表单正确预填，提交时调用更新回调而不是新增回调。
4. 编辑的相似推荐必须再次确认；完全重复和限制状态不能强行继续。
5. 删除必须经过二次确认，取消时不调用删除。
6. 删除失败时保留弹窗和资源名称，允许重试；成功后关闭。
7. Space 与 App 只组合 Hook 回调，不直接访问 API。

完整验收执行测试、TypeScript、ESLint、生产构建、生产依赖审计和 `git diff --check`。本阶段不以本地模拟登录代替自动化权限测试，数据库所有权仍由已经存在的 RLS/RPC 测试保证。

## 7. 方案取舍

- 采用右上角 `⋯` 菜单，而不是始终显示两个按钮：减少卡片噪音，并避免与公共 Mark 的视觉语义混淆。
- 复用表单组件，而不是复制一份编辑弹窗：新增和编辑具有相同字段校验与相似资源状态，复制会导致规则逐渐不一致。
- 采用硬删除加二次确认，而不是软删除：当前没有回收站或恢复需求；软删除会影响所有查询、唯一约束和容量统计，属于现阶段的过度设计。
