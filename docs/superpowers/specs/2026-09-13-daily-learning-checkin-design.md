# 每日学习打卡与本月记录设计

- 日期：2026-09-13
- 状态：待用户确认
- 范围：登录用户每日主动打卡一次，并在个人 Space 查看当月打卡记录

## 1. 目标与非目标

用户可以通过全站右下角按钮或个人 Space 中的按钮完成当天学习打卡。每天只能成功一次，完成后不可取消。个人 Space 用当月月历展示打卡结果，已打卡日期显示勾。

本阶段不追踪网页停留时长，不把打卡绑定到具体资源，不要求用户从外部资源返回，不提供历史补签、取消打卡、月份翻页、连续天数奖励、排行榜、提醒通知或学习笔记。

## 2. 业务规则

1. 未登录用户点击右下角“今日打卡”时，打开现有登录弹窗，不写入打卡记录。
2. 登录用户可以从右下角按钮或 My Space 的“本月学习记录”板块完成今天的打卡。
3. 两个入口共用同一个当天状态和提交动作；任一入口成功后，两个按钮立即同步为 `✓ 今日已打卡`。
4. 同一用户、同一当地自然日最多一条记录，由数据库约束保证。
5. 成功打卡后当天不可取消，界面不提供删除入口，数据库不提供客户端删除权限。
6. My Space 只展示用户当地当前月份，不提供上月、下月切换。
7. 已打卡日期显示勾；未打卡的过去日期和今天显示空白；未来日期显示为不可用状态。

## 3. 交互设计

### 3.1 全站右下角按钮

复用当前右下角的“今日打卡”入口，不新增重复悬浮按钮：

- 未登录：显示“今日打卡”；点击打开现有登录弹窗。
- 已登录且今日未打卡：显示“今日打卡”；点击后进入提交中状态，防止重复操作。
- 已登录且今日已打卡：显示带勾的“今日已打卡”，按钮不可再次提交。
- 网络失败：恢复为可点击状态并显示安全的重试提示，不误显示完成。

### 3.2 My Space 本月记录

在 Space 页顶部内容区增加紧凑的当月打卡月历。桌面端采用两栏：左侧月历固定约 `380px`，右侧浏览历史占用剩余空间并保持横向滚动；手机端改为月历在上、浏览历史在下。没有浏览历史时只显示左侧月历，不渲染空白占位卡片。两栏不强制等高。

月历标题显示动态月份，例如“9月打卡”，不再用第二行重复显示年份和月份。小号“今日打卡”按钮位于标题右侧。

板块展示当前月的星期标题和日期网格：

- 普通日期只显示数字，不绘制完整方形边框。
- 已打卡日期显示绿色实心圆和白色勾，勾替换日期数字。
- 今天未打卡时显示橙色圆形描边；今天已打卡时在绿色勾外增加橙色细圈。
- 月初前的占位格为空，不属于本月。
- 未来日期使用浅灰数字并禁止交互。
- 每个日期格提供可访问标签，例如“2026年9月13日，已打卡”。
- 月历本身不允许点击补签或取消。

若本月尚无记录，仍显示完整月历，而不是替换为空状态。读取失败时显示错误和重试入口，不影响 Space 中资源列表的使用。

## 4. 数据库设计

新增 `public.daily_checkins` 表：

| 字段 | 类型与约束 | 责任 | 数据示例 |
|---|---|---|---|
| `user_id` | `uuid`, `NN`, `FK -> auth.users.id ON DELETE CASCADE`, 联合 `PK` | 记录所属用户；删除账号时清除其打卡记录 | `6fda32b8-67a1-4b7e-b427-10a38c3d550c` |
| `checkin_date` | `date`, `NN`, 联合 `PK` | 用户打卡时所在时区的自然日 | `2026-09-13` |
| `checked_at` | `timestamptz`, `NN`, 默认 `now()` | 数据库实际写入时间，用于排序和排错 | `2026-09-13T08:30:00Z` |

`primary key (user_id, checkin_date)` 同时承担唯一约束与读取索引：

- 数据库级保证同一用户每天最多一条，覆盖连点、网络重试和绕过前端调用。
- 主键以 `user_id` 开头，适合按当前用户和日期范围读取当月记录，不需要另建重复索引。
- 不额外创建单独 `id`，因为“用户 + 日期”已经天然唯一，当前没有其他表需要引用一条打卡记录。

## 5. 日期边界

界面中的“今天”和“本月”按照用户浏览器所在地的自然日生成，前端向 RPC 传入 `YYYY-MM-DD`。数据库的 `checked_at` 始终由服务器生成，保留绝对时间用于排错。

RPC 只接受数据库 UTC 当前日期前后一天内的 `checkin_date`。这是一个轻量防护：兼容 UTC 两侧的主要时区，同时阻止任意历史补签。它不能证明用户的真实地理时区；若未来业务需要严格连续天数或奖励，再考虑在用户资料中保存 IANA 时区并由数据库计算当地日期。本阶段不为尚不存在的奖励系统增加这套复杂度。

## 6. 权限与数据库函数

表启用 RLS，并采用以下边界：

- 登录用户只能读取 `user_id = auth.uid()` 的记录。
- 撤销匿名用户和登录用户对表的直接插入、更新、删除权限。
- 打卡只通过 `check_in_today(checkin_date)` RPC 完成。
- RPC 使用 `auth.uid()` 决定所有者，不接受前端传入 `user_id`。
- 第一次插入返回 `checked`；主键冲突返回 `already_checked`，作为正常幂等结果处理。
- 不提供更新和删除 RPC，因此前端不能取消或改写已完成记录。

当月读取直接查询受 RLS 保护的 `daily_checkins`，范围为当前月第一天到下月第一天之前。每月最多返回 31 行，无需聚合 RPC、分页或汇总表。

## 7. 前端责任边界

| 单元 | 负责 | 不负责 |
|---|---|---|
| `src/api/` | 调用打卡 RPC；查询当前用户当月记录；映射返回结果 | 生成月历、渲染按钮、决定登录交互 |
| `src/service/` | 根据年月生成完整月历格子，并把打卡日期映射为已完成状态 | 直接查询 Supabase、持有 React 状态 |
| `useDailyCheckin` hook | 加载今日/当月状态、提交、防重复点击、错误处理和成功后同步刷新 | 绘制 UI、定义数据库权限 |
| 右下角按钮 | 展示登录、未打卡、提交中和已打卡状态；发出登录或打卡意图 | 直接调用 Supabase、维护独立打卡真相 |
| `MonthlyCheckinCalendar` | 展示当月月历、今天和打卡勾，并提供 Space 内打卡按钮 | 查询数据库、允许补签或取消 |
| `App` / `SpacePage` | 注入同一 hook 的状态与动作，组合现有页面 | 拼接 Supabase 查询或复制打卡规则 |

两个入口必须消费同一个 `useDailyCheckin` 实例，不能各自请求并保存一份状态，否则一个入口成功后另一个入口可能仍显示未打卡。

## 8. 数据流

```text
应用获得登录会话
→ 登录用户加载当地本月打卡日期
→ hook 计算今天是否已打卡
→ 右下角按钮与 Space 月历消费同一状态

任一“今日打卡”按钮
→ 未登录：打开登录弹窗
→ 已登录：check_in_today(localDate)
→ checked / already_checked：把今天加入本地状态
→ 两个按钮同步显示“今日已打卡”，月历今天显示勾
→ 网络或未知错误：保留未完成状态并允许重试
```

## 9. 错误与日志

- `already_checked` 是正常幂等结果，不记录为错误。
- 未登录点击是预期交互，只打开登录弹窗，不记录错误。
- 无效日期使用稳定业务错误码和安全提示，不展示数据库原始错误。
- 读取失败和提交失败记录结构化事件，例如 `daily_checkins.fetch.failed`、`daily_checkin.create.failed`。
- 日志包含 `operationId`、`errorCode`、`release`、`environment` 和操作名；打卡日期可以记录，因为它不包含私人资源内容。
- 不记录用户邮箱、access token 或 Supabase 原始会话对象。

## 10. 测试与验收

数据库测试：

1. 同一用户和日期第一次插入成功，第二次返回 `already_checked` 且仍只有一行。
2. 同一用户第二天可以再次打卡，不同用户同一天互不影响。
3. 用户只能读取自己的记录。
4. 匿名调用、越界日期、直接插入、更新和删除被拒绝。
5. 删除用户时关联记录按外键规则清理。

前端测试：

1. 未登录点击右下角按钮打开登录弹窗，不调用打卡 API。
2. 登录用户可以从两个入口打卡；提交中阻止重复点击。
3. 任一入口收到 `checked` 或 `already_checked` 后，两个按钮和今天日期格同步完成。
4. 网络失败时不显示已完成并允许重试。
5. 月历正确处理每月天数、月初星期偏移、闰年、今天、未来日期和已打卡日期。
6. Space 月历位于顶部内容区，按钮在桌面与手机布局正确。
7. 月历具有日期级可访问标签，且不提供补签或取消交互。

完整验收运行前端测试、TypeScript、ESLint、生产构建、数据库测试和 `git diff --check`。远端 Supabase migration 必须先在本地数据库验证，再由用户单独确认是否应用；前端部署不隐式修改数据库。

## 11. 方案取舍与复查条件

- 采用每日主动打卡，而不是停留时长：含义清楚、实现可靠；代价是不能表达学习量差异。
- 采用当月月历，而不是 GitHub 年度热力图：移动端易读且与轻打卡匹配；代价是暂时看不到长期趋势。
- 采用联合主键，而不是额外自增 ID：业务键已经天然唯一，并直接支持主要查询；如果未来其他表需要引用单次打卡，再评估独立 ID。
- 两个入口复用同一 hook，而不是各自管理状态：避免 UI 不一致；代价是需要在 App 层统一持有状态。

可迁移的工程判断：如果两个界面表达的是同一份业务事实，就应共享一个状态来源，并让数据库约束最终真相，不能靠两个组件各自保持一致。
